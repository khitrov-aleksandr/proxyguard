# ProxyGuard

## Общее описание
| Поле | Значение |
| --- | --- |
| Service ID | `proxyguard` |
| Service name | ProxyGuard |
| Responsibility | Прозрачный reverse proxy перед SMS-ендпоинтами сайта и мобильных приложений. Блокирует подозрительные запросы по набору антиспам-фильтров и либо проксирует трафик в backend, либо возвращает фейковый/ошибочный ответ. |
| Owner | Уточнить у команды сопровождения и заполнить перед merge |
| Repository | Уточнить ссылку на GitLab/SCM |
| Status | Active |

## Назначение
Сервис снижает количество спам- и бот-запросов на отправку SMS-кодов, чтобы сократить расходы и уменьшить нагрузку на backend-системы авторизации и регистрации.

## Технологический стек
| Компонент | Используется |
| --- | --- |
| Язык | Go `1.23` |
| HTTP framework | Echo `v4.12.0` |
| Reverse proxy | `net/http/httputil` |
| Хранилище счетчиков и блокировок | Redis |
| Логирование | `zerolog`, файловые логи |
| Контейнеризация | Docker, Docker Compose |
| CI/CD | GitLab CI |
| Мониторинг | Отдельный HTTP monitor endpoint на `MONITOR_PORT` |
| Брокеры / очереди | Не используются |
| База данных | Не используется |

## Архитектура
ProxyGuard работает как промежуточный слой между внешним `nginx` и backend-сервисами, которые реально отправляют SMS или регистрируют пользователя. На каждый входящий запрос сервис:

1. Пишет входящий запрос в `all`-лог.
2. Применяет набор фильтров по URI, телефону, cookies, сессии, IP, `X-Device-Id` и регистрационным признакам.
3. Если фильтр срабатывает, не отправляет запрос в backend и возвращает локальный ответ.
4. Если фильтры не сработали, проксирует запрос в целевой backend.
5. Для пропущенных запросов пишет запись в `accepted`-лог.

## Основные сценарии
### 1. Сайт: отправка SMS
Источник данных: web-клиент -> внешний `nginx` -> ProxyGuard -> backend сайта.

Что делает сервис:
1. Проверяет `POST /api/customer/auth-sms`.
2. Применяет rate limit по телефону: не более `3` запросов за `100` секунд.
3. Проверяет связку `shop_session + phone`.
4. Проверяет наличие обязательных cookies.
5. При успехе проксирует запрос в backend сайта.
6. При блокировке возвращает `429`.

### 2. Мобильное приложение: регистрация
Источник данных: мобильный клиент -> ingress/nginx -> ProxyGuard -> backend мобильного приложения.

Что делает сервис:
1. Сохраняет счетчики GET-запросов для пары `ip + X-Device-Id`.
2. Проверяет `POST /api/v8/manzana/registration`.
3. Блокирует запрос, если до этого было меньше двух GET-запросов.
4. Блокирует некоторые сценарии по `gmail.com`, телефону и email.
5. При блокировке не идет в backend и возвращает локальный успешный ответ-заглушку.
6. При успехе проксирует запрос в backend нужного бренда.

### 3. Мобильное приложение: логин по SMS
Источник данных: мобильный клиент -> ingress/nginx -> ProxyGuard -> backend мобильного приложения.

Что делает сервис:
1. Проверяет `POST /api/v8/ecom-auth/login-sms-prestep`.
2. Учитывает результаты предыдущих фильтров регистрации.
3. Ограничивает количество попыток по телефону и `X-Device-Id`.
4. При блокировке возвращает `429`.
5. При успехе проксирует запрос в backend нужного бренда.

## Фильтры и бизнес-правила
### Сайт
1. Rate limit по телефону: `3` SMS за `100` секунд.
2. Проверка по cookie `shop_session` и телефону:
   - один телефон в одной сессии: стандартный лимит `3 / 100 сек`;
   - одна сессия и несколько телефонов: усиленный лимит `3 / 86400 сек`.
3. Блокировка при отсутствии хотя бы одной из cookies:
   - `_ga`
   - `rrpvid`
   - `rcuid`
   - `_ym_uid`
   - `advcake_track_url`
   - `advcake_track_id`

### Мобильное приложение
1. Для всех GET-запросов сохраняется активность по `ip + X-Device-Id`.
2. Окно хранения счетчика GET-запросов: `1800` секунд.
3. Для регистрации:
   - блокировка, если было меньше двух GET-запросов;
   - блокировка по email из домена `gmail.com`;
   - блокировка по телефону, если используется несколько email;
   - блокировка по телефону на `1800` секунд.
4. Для логина:
   - блокировка, если ранее сработал фильтр регистрации;
   - блокировка, если было более двух попыток регистрации на один телефон за `1` минуту;
   - блокировка, если один `X-Device-Id` использован для разных телефонов;
   - блокировка по телефону и `X-Device-Id` на `1800` секунд.

## Ключевые ограничения
| Ограничение | Значение |
| --- | --- |
| Site phone rate limit | `3` запроса / `100` секунд |
| Site session heavy limit | `3` запроса / `86400` секунд |
| Mobile GET activity TTL | `1800` секунд |
| Mobile phone/device block TTL | `1800` секунд |
| Registration burst check | более `2` попыток за `1` минуту |
| SLA | Не задокументирован в репозитории |
| Таймауты HTTP клиента / proxy | Явно не настроены, используются стандартные значения Go |

## Внешние зависимости
| Зависимость | Назначение | Что будет при отказе |
| --- | --- | --- |
| Redis | Счетчики, TTL, блокировки | Фильтры перестанут работать корректно, сервис не сможет надежно принимать решение по блокировке |
| Backend сайта (`SITE_BACKEND_URL`) | Реальная отправка SMS для сайта | Запросы сайта не будут обработаны backend-ом |
| Backend МП OZ (`MOBILE_BACKEND_URL_OZ`) | Реальная регистрация/логин бренда OZ | Запросы бренда OZ не дойдут до backend |
| Backend МП SF (`MOBILE_BACKEND_URL_SF`) | Реальная регистрация/логин бренда SF | Запросы бренда SF не дойдут до backend |
| Backend МП SA (`MOBILE_BACKEND_URL_SA`) | Реальная регистрация/логин бренда SA | Запросы бренда SA не дойдут до backend |
| Backend МП ST (`MOBILE_BACKEND_URL_ST`) | Реальная регистрация/логин бренда ST | Запросы бренда ST не дойдут до backend |
| Внешний ingress / nginx | Точка входа трафика | Клиентский трафик не попадет в сервис |

## Требования для запуска
Для локального запуска нужны:

1. Docker и Docker Compose.
2. Файл `.env` на основе `.env.example`.
3. Доступ к сети/хостам, указанным в backend URL, если требуется проксирование в реальные окружения.
4. Для запуска вне Docker потребуется Go `1.23` и доступный Redis.

## Локальный запуск
1. Создайте `.env` на основе `.env.example`.
2. Проверьте значения backend URL и `REDIS_ADDR`.
3. Запустите окружение:

```bash
docker compose run --rm --service-ports --build cli
```

4. Внутри контейнера запустите приложение удобным для команды способом, например через `go run .` или `go test ./...`.

Примечание: в репозитории есть `Dockerfile` для сборки runtime-образа и `Dockerfile.cli` для dev-контейнера.

## Мониторинг и диагностика
### Monitor endpoint
Сервис поднимает отдельный HTTP endpoint на `MONITOR_PORT`. На любой запрос он отвечает `200 OK` с JSON:

```json
{
  "status": "success",
  "message": "monitor response"
}
```

### Логи
Используются файловые логи:

- `logs/site/all.log` - все входящие site-запросы.
- `logs/site/accepted.log` - site-запросы, пропущенные в backend.
- `logs/site/handle.log` - причины блокировок сайта.
- `logs/mobile/all-*.log` - все входящие mobile-запросы по брендам.
- `logs/mobile/accepted-*.log` - mobile-запросы, пропущенные в backend.
- `logs/mobile/handle-*.log` - причины блокировок mobile-запросов.
- `logs/monitor.log` - обращения к monitor endpoint.
